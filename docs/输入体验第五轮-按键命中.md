# 输入体验第五轮 · 按键命中与整句排序

在相同的 6,936 个带噪触点上，中文 26 键少错了 **48 个字母**，用同一解码器比首选，多打对了 **6 个整句**。在没有触点噪声的排序评测里，正确全拼首选从 **188/246 到 196/246**，聊天简拼从 **28/71 到 32/71**。这些是 Windows 的 Python 回放结果。上一版的 Swift 数字取自 build 87 的 macOS CI，当前版的 Swift 耗时、名次和 iPhone 手感待验证。

## 三个触摸假设

| 假设 | 核实结果 | 本轮处理 |
|---|---|---|
| 键区只看几何 | build 87 的 `KeySurfaceView.swift:299` 对键内触点直接返回，对键间触点比较到矩形的距离。相同的 a/s 边界在 `zh` 后也会选 s。 | 仅在中文 26 键的字母边缘结合合法拼音续接与距离。按下时读取当前组字上下文，双拇指交替时先处理上一键。 |
| 手指轻微滚动会换键 | 旧版同文件约第 465 行只检查当前键外扩横向 6、纵向 8 pt 的矩形。靠边按下时，轻移十几个点就能跨过它。 | 第一次换键同时要求离开外扩矩形，且离按下点至少半个键宽。开始有意滑动后按几何选择，松手提交当前位置。 |
| 触点通常偏低 | 仓库没有这名用户的真实触点。相同噪声下，额外向上补偿 2 pt，在设定下偏 3 pt 时比零补偿再少错 7 个字母。无下偏时两者的字母错误数只差 1 个。 | 只给边缘字母之间的距离计算加 2 pt 补偿。保留零补偿回放，真机复查上下排误换。 |

命中时先走旧几何判定。键帽中央宽、高各 60% 直接返回。外围只考虑两个方向都在 0.78 个键距以内的字母键，取归一化中心距离平方最小者，合法续接减 0.24。键距取实际布局的键宽、键高和间距，随横屏与键盘高度一起变化。每次组字更新从最近手动分隔处求出所有可达音节边界，把可接字母存为 26 位掩码。首次换键位移门槛为键宽的 0.52 倍，限制在 16–24 pt。[命中与滑动](../ios/AIKeyboardExtension/Keys/KeyHitResolver.swift) · [组字上下文](../ios/AIKeyboardExtension/Core/KeyboardSession.swift) · [触摸入口](../ios/AIKeyboardExtension/Keys/KeySurfaceView.swift)

英文、Shift、九宫格、功能键及没有可达拼音前缀的输入使用几何判定。中文混输时，如果几何命中字母能把已输入串续成英文词表前缀，也保留几何选择。英文检查只在即将换字母时运行，直接在已排序的映射文件上按行二分。比如 `zh` 后轻触偏 s 的边界可选 a，`b` 后在同一点可保留 `bs`，继续输入 `bsc`。[英文词表查询](../ios/Shared/IMECore/EnglishLexicon.swift)

## 整句为什么会输给同音字

1. **目标词已在词库，也能映射到 libime。** 实查 `diancai` 下“点菜”的词频为 219，高于“垫材”的 54。同样，“谁”12,455、“睡”5,023，“挑”和“填”分别在各自同音组第 4 位，都能进入前八词块。build 87 仍把“你先点才”“表格天好了”放在首选。词模型比较不同切法时，拆成单字的高频路径可能压过整词，短历史、未收录词对和语料文体都会影响排序。
2. **相同文字过早合并。** 在 `xianchidiandongxi` 中，读完 `xianchi` 时，“先吃”整词和“先／吃”单字路径提供不同的词历史。build 87 在中途按相同文字去重，强的“吃／点／东西”续接只留在“现／吃”那条路。实测仅加字概率仍选“现吃点东西”。保留不同历史后才选出“先吃点东西”。现在启用字模型时，中途按前词历史及末两字合并，句末按上屏文字去重，每个位置最多四条路径。[整句解码，约第 648、670 行](../ios/Shared/IMECore/PinyinEngine.swift)
3. **简拼的词级分数能颠倒口语候选。** build 87 已把“我还没吃饭”“我们明天见”放在第二。“今天吃什么”也进入可重排的口语路径。现在只对已有至多 24 条简拼末端路径增加字级口语分，并计算词典独立解码首选的一致性以及已有人工词对的精确匹配。没有增补这些测试句的拼音映射。[简拼重排，约第 123 行](../ios/Shared/IMECore/ChatInitialsModel.swift) · [人工词对查询](../ios/Shared/IMECore/NextWordIndex.swift)

新增的小模型来自仓库既有的 Tatoeba 中文快照。以连续简化汉字片段训练，排除与评测目标完全相同的子句，保留出现至少两次的字对和三字组。二元 62,957 条，三元 102,676 条，带句首、句末与平滑回退，自然对数按 1/256 量化。随包文件 **1,587,224 字节（1.51 MiB）**，SHA-256 为 `9cea464cd5e354c21db2fd8c2d2bef916f343b8440656209530b6bab45a76dc5`。Windows 已从快照重建得到同一摘要。Swift 只读 mmap，索引直接查文件，每次转换结束释放字级查询缓存。38、54 字母性能用例在 Python 分别查到 554、1,164 个不同的三字组；错键长句走原有纠错路径。文件大小是映射上限，真机常驻页及瞬时缓存占用待测。[模型生成](../tools/dict/character_model.py) · [读取器](../ios/Shared/IMECore/CharacterLanguageModel.swift) · [来源与署名](../THIRD_PARTY_NOTICES.md)

全拼仅在可完整切分、整键无词典直接命中、无手动分隔和已确认左词时叠加字模型。为避免重复计算词频并控制小语料的稀疏惩罚，各字使用 `0.75 × (max(条件对数概率, 一元对数概率 − 2) − 0.5 × 一元对数概率)`。词长证据区分句首与句末的多音节歧义，防止把“切一块蛋糕”拆成“企鹅一块蛋糕”。简拼在原整数分制上用 16 倍字级原始分、词典一致首选加 144、人工词对按后词字数加 96 或 192。纠错两侧用同尺度的词模型比较。手动选词、九宫格、余串继续使用 build 87 的对应路径。

## 验收与真机复查

Windows 已运行 `final_acceptance.py`，结果为 **GO**。六个闸门通过，工程结构通过 86 项检查，P0、P1、未定义符号均为 0，Swift 静态检查列出 7 项 P2 建议。

- **macOS CI** 会跑原有的三版本 Swift 对比，另逐类检查 build 87 的首选与前三下限、纠错四项全零。新增字模型映射、跨词块三元、稀疏回退、缓存两种分制，以及“今天谁值班”“先吃点东西”等八条完整消费输入的首选回归。重点看正确全拼、短句、盲集、聊天简拼是否达到上表收益。[回归入口](../tools/imecheck/main.swift)
- **触点与耗时**。CI 打印三个宽度的字母错误和最终整句首选数，合计两者都须不劣于旧几何；另打印按下判定和组字前缀准备的 P95。按下判定门槛 50 微秒。38 字母、54 字母和带错长句仍分别限 5、10、20 ms；build 87 实测 0.91、2.06、5.83 ms。当前版 Windows 无 Swift 编译器，未以 Python 时间代填。
- **工程与复现**。`ios/project.yml` 的 `AIKeyboardExtension`、`Shared` 和 `Shared/dict` 目录已覆盖新源与资源，已同步生成的 Xcode 工程。当前版 imecheck 的 swiftc 清单加入真实键位布局、命中器、字模型及触点回放。可用 `python tools/dict/lm_eval.py --characters` 和 `python tools/dict/touch_eval.py` 复现两张主表，`--offset 0`、`--bias 0` 可重放补偿对照。[CI 配置](../.github/workflows/build.yml)
- **iPhone**。在惯用握姿下轮流试中心快点、`zh` 后贴 a/s 边界点、双拇指交替和按住横滑换键。分别试单手、横屏和自定义高度；观察上下排是否由“常偏下”变成“常偏上”。再试中文混输 `claude`、`github`，以及上滑符号、退格和空格移光标。用 Instruments 看首次使用与连续长句的命中时延、转换延迟和扩展峰值内存。
