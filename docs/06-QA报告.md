### 10.3 根因层面的"无法绕过"

> ⚠️ **先看这一条**：下表前三条是**平台限制**（Apple / iOS 的硬约束），**不是我们没做完**。它们的共同特征是"当前免费签名/键盘扩展的能力边界就在这儿"，付费或换能力后无需改代码即可打通。列在这里是为了让使用者知道"为什么这功能看起来缺一块"，而不是当成缺陷。

| 问题 | 根因 | 结论 | 性质 |
|---|---|---|---|
| 生图结果不能直接插入输入框 | `UITextDocumentProxy` 协议只有 `insertText(_:)`，**没有插图片的 API**；键盘扩展只能向宿主写入纯文本 | 无解；降级为「复制图片」→ 用户在聊天窗口长按粘贴 | 🔒 平台限制 |
| App 与键盘配置不共享 | 免费签名无 App Group capability（`com.apple.security.application-groups` 需付费账号） | 已用「同步到键盘」（具名剪贴板 `com.moyu.config`）绕过；`SharedStore` 自动降级到 `UserDefaults.standard` | 🔒 平台限制 |
| ~~宿主 App「保存到相册」未实现~~ | 已在 v1.2 补齐（`NSPhotoLibraryAddUsageDescription` + `PhotoLibrarySaver`，只申请 `.addOnly`） | **已实现**：生图结果卡片上有「保存到相册」按钮 | ✅ 已闭环 |
| 必须在 macOS 上编译 | Apple 的签名/工具链限制 | 已用 GitHub Actions 绕过 | 🔒 平台限制 |
| 7 天必须重签 | Apple 免费账号策略 | 已用 iloader 化简为 5 分钟 | 🔒 平台限制 |

**补充说明（三条"未闭合"其实是设计取舍，不是缺陷）**：

1. **免费签名下 App Group 不可用 → 扩展心跳 App 侧读不到**。
   具体表现：键盘扩展里由 `KeyboardViewModel` 写入的统计/心跳数据，宿主 App 侧读不到。
   原因：无 App Group 时 `SharedStore` 降级到各自的 `UserDefaults.standard`，宿主 App 与键盘扩展是**两个独立进程、两个独立沙盒**，`UserDefaults.standard` 互不可见（不是"写失败"，而是"本来就看不见"）。
   这是**安全降级不是 bug**：不共享比强行放宽安全边界更安全，且 App 侧不会因此崩溃 —— 它只会看到"没有数据"。
   付费开 App Groups 后会**自动打通，代码零改动**（`SharedStore.isAppGroupAvailable` 已是运行时判断）。

2. **生图结果无法直接插入聊天输入框**。
   键盘扩展仅能通过 `UITextDocumentProxy.insertText(_:)` 向宿主输入框写入**文本**，iOS 未提供向输入框写图片的 API。
   所以生图能力的最终一步必然是：键盘里点击「复制图片」（写入 `UIPasteboard.general.image`）→ 用户在微信/短信等聊天窗口的输入框**长按 → 粘贴**。
   这是全行业所有 AI 键盘 App 的共同限制，不是本项目独有。

3. ~~**宿主 App「保存到相册」未实现**~~ → **v1.2 已补齐（2026-10-25）**。
   历史记录：v1.1 及以前只提供「复制图片」，`NSPhotoLibraryAddUsageDescription` 与 `PHPhotoLibrary` 相关代码完全没写。
   v1.2 新增 `ios/AIKeyboard/Support/PhotoLibrarySaver.swift`（只申请 `.addOnly` 权限，`performChanges` 写入），生图结果卡片上带「保存到相册」按钮，失败时给中文文案与「去设置 › 隐私 › 照片」的恢复建议。
   设计上仍保持**只在用户点按钮时**申请权限，不在 App 启动时弹授权框。
   注意：这条能力只存在于**宿主 App**；键盘扩展没有该权限（`PHPhotoLibrary` 在 extension 里用不了，也不该用）。

### 10.5 用户真机测试反馈的两个 AI 链路 bug（v1.1.1 修复记录）

上一轮装机自测时用户报了两条：**「编辑服务商 → 保存完 API Key → 点测试连接没反应」**，以及**「AI 试验场调用协议有 bug，压根没法测」**。两条都是真 bug，根因不同，记录如下。

#### Bug A：测试连接点了没反应 —— 客户端被提前释放，流以 `cancelled` 静默结束

`ConnectivityProbe.makeHelloStream(config:apiKey:)` 的写法是：

```swift
let client = AIClientFactory.makeLLM(config: config, apiKey: apiKey)  // ← 局部变量
let request = ChatRequest(messages: [ChatMessage.user("hi")], temperature: 0, maxTokens: 8, stream: true)
return client.stream(request)                                          // ← 函数返回，client 立刻释放
```

而三个 LLM 客户端（`OpenAICompatibleClient` / `AnthropicClient` / `GeminiClient`）的 `stream()` 当时都写成 `Task { [weak self] in guard let self else { continuation.finish(throwing: AIError.cancelled); return } … }`。于是：

`makeHelloStream` 返回 → `client` 引用计数归零 → `Task` 里的 `weak self` 变 nil → 流立刻以 `AIError.cancelled` 结束 → `ConnectionTester.test()` 的 `catch` 命中 `case AIError.cancelled: state = .idle; return` → **UI 回到初始态，表现为「点了完全没反应」**（连 loading 都一闪而过）。

**修法**：三个客户端的 `stream()` 由 `Task { [weak self] … }` 改为 `Task { [self] … }`。安全性说明：`continuation.onTermination = { _ in task.cancel() }` 只持有 `task`，`task` 持有流与 client，流结束即整体释放，**不构成引用循环**；而 `[self]` 正是 Swift 并发里「异步流要活到消费者取消为止」的标准写法。改三处覆盖全部 4 个调用点（`TestConnectionView` / `ProviderListView` / `DiagnosticsChecklist` ×2），调用方签名零改动。

> 教训：`[weak self]` 不是万能正确的默认值。**返回 `AsyncStream`/`AsyncThrowingStream` 的方法必须让 `self` 活到流结束**，否则消费者拿到的是「立刻就结束的流」；而 `AIError.cancelled` 又天然被上层当成「用户主动取消」静默忽略，bug 就被吞得干干净净。

#### Bug B：AI 试验场调不通 —— 三处协议兼容性问题叠加

| # | 问题 | 影响 | 修法 |
|---|---|---|---|
| B1 | `OpenAICompatibleClient.makeBody` 对流式请求无脑加 `"stream_options": {"include_usage": true}` | `stream_options` 是 OpenAI 专有参数。**DeepSeek 部分版本、通义 `compatible-mode`、Kimi、智谱 GLM、硅基流动、部分 OpenRouter 模型会直接 400 `Unrecognized request argument supplied: stream_options`** | 整段删除。流式侧 usage 本来就没被使用（`runStream` 里 `_ = usage`），删掉零功能损失，换来所有兼容端点可用 |
| B2 | `HTTPTransport.makeJSONRequest` 把 `Accept` 固定成 `application/json`，SSE 流式请求也用它 | 严格要求 `Accept` 的网关会按普通 JSON 处理（一次性返回完整结果）甚至 406，客户端按 SSE 解就是空的 | `makeJSONRequest(…)` 增加 `accept: String = "application/json"` 参数；三个客户端的 `runStream` 传 `accept: "text/event-stream"` |
| B3 | `runStream` 只按 SSE 解析，服务端忽略 `stream: true` 直接返回完整 JSON 时，`parseStreamPayload` 全返回 nil | 用户看到「服务商没有返回内容」，把问题归因为「协议有 bug」 | 增加**非流式二级兜底**：累加原始字节（上限 1 MB），若整段流一个正文字符都没拿到且缓冲以 `{` 开头，则按 `parseCompletion` 再解析一次，把完整回复一次性吐出 |

另外补了一处**用户体验**问题（不是协议 bug，但会让用户以为「试验场坏了」）：

- `PlaygroundActionSection.canGenerate` 原来只查 `appState.isChatReady`（= baseURL + model 非空），**不查有没有填 API Key** → 按钮可点，点下去只弹一张失败卡片。现在 `canGenerate` 增加 `hasKeyForCurrentProvider`，`generateDisabledReason` 补上「「X」还没有填 API Key，去「设置 › AI 服务」补上」。
- `PlaygroundView.featureChips` 原来遍历 `AIFeature.allCases`（含新增的 `.chat` / `.suggestion` / `.custom`）→ 试验场里出现「AI 对话」「智能联想」两个单轮语义不对的能力，以及没有独立入口的「自定义」。现在固定为 `playgroundFeatures = [.polish, .expand, .translate, .replySuggestion, .image]`。

> 教训：**「OpenAI 兼容」不是「OpenAI」**。`stream_options`、`max_tokens` 之外的新参数、`Accept` 的严格性、`stream: true` 是否真的被尊重，各家都可能不一样。兼容层必须按「最小公共子集」发请求，并且**对「服务端没按流式回」这种合法但少见的情况有降级路径**，否则用户只会看到一句「没有返回内容」。

**验证状态**：`scripts/qa/static_check.py` → 124 文件 / 30,399 行 / **P0=0 P1=0 P2=0**；本地六闸门全绿。真机验证要等下一次签名安装（这两条都属于「必须打真包才能确认」的类型）。

## 12. 附：怎么自己跑这些脚本

```bash
# 在仓库根目录执行（Windows / macOS 都行，只要 Python 3.8+，零第三方依赖）

# ⭐ 一条命令跑完六个闸门 + GO/NO-GO 结论（推荐）
python scripts/qa/final_acceptance.py
python scripts/qa/final_acceptance.py --md docs/06-QA报告.md --inject   # 顺便回填本报告 §9.3

# 单个脚本
python scripts/qa/static_check.py                    # Swift 静态检查
python scripts/qa/project_check.py                   # Xcode 工程结构
python scripts/qa/consistency_check.py               # 设计令牌一致性
python scripts/qa/link_check.py --all                # 文档死链（全部 Markdown）

# 工程生成 / 结构校验（ios-skeleton）
python scripts/gen_xcodeproj.py --check              # 只检查工程是否滞后于磁盘
python scripts/gen_xcodeproj.py                      # 真正重新生成 pbxproj
python scripts/validate_project.py                   # 85+ 项结构校验

# 机器可读 / 存档
python scripts/qa/static_check.py --json             # JSON 输出
python scripts/qa/static_check.py --md report.md     # Markdown 输出
python scripts/qa/static_check.py --skeleton docs/06-QA报告.md   # 重新生成报告骨架

# 退出码：0=通过  1=有 P1  2=有 P0  3=脚本内部错误
# final_acceptance.py 的退出码：0=GO  1=CONDITIONAL GO  2=NO-GO  3=内部错误
# 所以可以这样在 CI 里卡门禁：
python scripts/qa/final_acceptance.py || exit 1
```

**脚本设计原则**（为什么敢信这些数字）：

1. **零第三方依赖** —— 只用 Python 标准库，任何有 Python 的机器都能跑，不会因为装不上 `pyflakes` 而失效。
2. **不误报优先于不漏报，但"确定是错的"必须报 P0** —— 未定义符号检查分两级：本项目自造 UI 类型特征（后缀 `View`/`Card`/`Sheet`/`Panel`/`Rows`… 或前缀 `KM`/`AI`/`Key`/`Candidate`…）判 **P0**（系统 SDK 不可能有这种命名，缺了必挂）；其余标 **P2 `[粗查]`**。白名单 `SYSTEM_TYPES` 收录了 500+ 个 Swift/SwiftUI/UIKit/Foundation 类型，宁可漏也不天天假警报。
3. **每条 P2 都有"为什么它是 P2"的注释** —— 比如 `DUP-DECL` 曾经是 P2，后来发现 Swift 的 `invalid redeclaration` **连 `private` 都不放过**，才上调为 P0；再比如 `SYMBOL-UNDEFINED` 曾经全判 P2，`KeyboardRootView` 引用 8 个不存在的视图时被"P2 不阻塞"放过，才拆成两级。
4. **自己的 bug 自己修** —— 本轮修了 11 个脚本自身的误报/漏报（详见脚本内注释）：嵌套 `CodingKeys` 误判、泛型参数误判、字符串插值误判、负数令牌误判、模型名误判、`AsyncImage` 等类型漏白名单、`{{…}}` 模板占位符误判、`productType` 引号解析、缩写路径片段误判、gesture 类型漏白名单、`ABC`/`QWERTY` 布局名误判。
5. **一条命令出结论** —— `final_acceptance.py` 串起六个闸门 + `SYMBOL-UNDEFINED` 一票否决，自动识别「派生 P0」（gen 漂移导致的 membership 假阳性会被合并计为 1 个根因），避免把同一个问题数成 3 遍让人误判严重性；报告片段还会自动 `_sanitize`（去反引号、`|`→`/`），防止注入内容被 `link_check` 二次扫描成自我引用的假死链。
