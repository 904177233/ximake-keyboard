# 输入体验第三轮

本轮针对 3.0.11 build 84（`bc29905`）的三项真机反馈。工作区已有修复和三版 Swift 对照入口。下面的命中数来自 Windows 的 Python 实验，macOS 的实际名次、耗时和 iPhone 首键延迟仍待回测。

## 从反馈追到候选

| 现象 | build 84 中的证据 | 工作区修改 |
|---|---|---|
| `nzgsm` 首选「你这个什么」，`ncflm` 首选「年初富勒姆」 | 查随包词典，两串都没有整键词。按键组最高词频，`nzg` 的「你这个」为 1053，`flm` 的「富勒姆」为 133，均居组内第一。`gsm` 的「干什么」和 `zgsm` 的「在干什么」也都居组内第一。两例的正确词块本就在 12 键召回范围内。见 build 84 的 `PinyinEngine.swift:303`。 | 对 4–12 个纯声母的连续输入，用中文句子训练的一元及二元分数单独解码，包括句首、句尾。保留通用解码结果及逐词选词，模型返回真实词段和各段消耗的声母数。见 `ChatInitialsModel.swift:56`。 |
| 拼音栏显示 `nzg'sm`、`nc'flm` | build 84 的 `PinyinEngine.swift:1128` 把无完整音节的整个词块作为显示单位；候选被提升后，拼音栏仍取原始最优路径。 | 纯简拼按输入声母逐个显示；混拼只拆开其中的简拼块。整键提升时按该词的实际边界显示。 |
| 常用词和第二候选 | build 84 的 `PinyinEngine.swift:787` 先放两条备选，再从已混排列表找整词提升。上下文、学习和纠错随后都能改写首位。 | 先独立求整键词。完整双音节词可以排在两个单字拼成的句子前面，整词候选在整句备选前得到位置。余串优先匹配已确认前词的完整候选，当前输入下仍有效的个人选择最后决定首位。 |
| 打对也被纠错 | build 84 的 `PinyinEngine.swift:832` 以候选数量启动单词纠错，840–844 行又按整句分差抢第一或插第二。合法短句照样经过两条分支。原音节判定只检查最少音节的一种切法，并受长串长度限制。 | 用可达性判断是否存在符合手动分隔的合法全拼切法，完整全拼排除简拼和未完成的词块。两种纠错共用门控。完整全拼的短串只在前三之后保留纠错，已有整键命中或较长完整全拼跳过整句纠错。切不开的输入仍按分差竞争；纠错路径的改动前后都必须由精确块组成。 |
| 中文模式打 `claude` | wordfreq 表已有 `claude`，每十亿词 5750 次。build 84 的 `KeyboardSession.swift:535` 仅在英文输入时查询英文表，中文转换最后才尝试添加原文，候选达到上限后还可能添加失败。 | 中文 26 键复用英文词表，保留输入大小写。精确英文且无完整中文解读时可排第一；有完整全拼时优先中文。三字母起支持前缀补全，如 `claud → claude`。只补录一个缺失名称 `chatgpt`。 |

原始简拼词块每多一个声母加 3 分，单字声母另扣 10 分。拆成几个块及块间频率直接影响句子总分。chat_priority 在宽候选列表中有用，原整句简拼词块只使用通用词频；构建时混合的 Rime essay 也是单词频率。已确认两条路径都缺少句子级证据。尚无证据能把所有分词错误归因于 3 分的词对奖励或 2 分的字界奖励，普通全拼与九宫格仍沿用这些分数。另保留每键 3 个精确词的热路径，未全面扩宽 DP。[解码器](../ios/Shared/IMECore/PinyinEngine.swift) · [词频构建](../tools/dict/build_binary.py)

聊天简拼合并实验首选**修回 17 条，引入 9 条新错**。`nzgsm` 在模型消融中从「你这个什么」变为「你在干什么」，`ncflm` 从「你厨房里吗」变为「你吃饭了吗」。短简拼前三有损失，因此模型启用下限为 4 个声母。盲集里的三条纯简拼均超过 12 个声母，长句结果持平反映了启用范围。其他输入仍受本轮候选排序与纠错改动影响，需看完整 Swift 对照。已有 Python DP 不含手机上的全部句末替换、学习及最终候选逻辑。

另对长句的三个原始备选做了词对重排实验。开发集权重 0、0.5、1、2 的首选都为 8/28，按并列时取较小权重选中 0。冻结盲集仍为 6/27，修回 0 条、新错 0 条。因此没有把普通全拼整句的上下文打分替换成这个模型。

两条旧纠错断言更新为开关纠错前三相同、指定纠错词仍在第四。`xiexienu` 可读作 `xie'xie'nu`，`nihaohaoma` 可读作 `ni'hao'hao'ma`。强行将「谢谢你」「你还好吗」排第一或第二与保护合法输入冲突。另把英文 `hello` 必须在列表末尾改为前三可直接选，同时单测未知串原文兜底。保留 `nihap`、`woxiangchifna` 等非法输入纠错首选测试，保留原有性能阈值。[功能断言](../tools/imecheck/main.swift)

## CI 和真机要看的数字

CI 取 `ead215a`、`bc29905` 和工作区三份 Swift 源码，各用自己的词库、联想表及发布热词。共用同一驱动、空个人学习库、关闭模糊音，逐条开关纠错。历史 3.0.10 按当时的余串接口运行。新评测有 **498 条**，包含 71 条聊天简拼、43 条其他简拼、41 条中文模式英文、28 条 16–22 字长句、30 条余串、52 条单编辑错键；另跑 27 条原冻结盲集。余串直接给引擎已确认前词，未走 UIKit 点击事件。[语料](../tools/dict/ime_bench.tsv) · [Swift 驱动](../tools/imecheck/Benchmark.swift) · [逐条对照](../tools/imecheck/compare.py)

1. 看「简拼整句」的首选、恰在第二、前三，以及 build 84 第二升第一、修回和新增错误。门槛为首选净增至少 2 条、前三不降；两条反馈要求首选文本和拼音栏同时正确。每类输出前 15 条首选未命中的实际前五。
2. 看 246 条正确全拼（含显式分隔与余串）中纠错占第一、占第二、挤掉自然第二目标和使目标掉出前三的计数。四项门槛均为 0。看四类错键各 13 条的首选、前三以及命中时真正标为纠错的数量；打错后仍为合法拼音的样例有意保留。
3. 看冻结盲集整句首选、前三、逐字同位置命中。首选与前三按本次同机 build 84 动态设下限。对比 3.0.10 的逐类退步样例，区别词典变化、原自然候选已错和纠错新增的干扰。准确归因仍需 CI 的实际候选。
4. 看 41 条英文的首选与前三、`claude` 的精确首选、`claud` 的补全及合法音节 `can` 的中文首选。检查小写、大写、空格接受和中文余串中选英文的上屏结果。
5. 看原有三个热循环平均耗时。build 84 的 CI 分别为 **3.43、4.73、11.29 ms**；上限 **5、10、20 ms**。这些循环没有测真机 P95。真机需另外测键盘冷启动后第一次查英文、首串简拼和连续退格重输时的逐键延迟及扩展内存峰值。

新模型 **2,221,743 字节（2.12 MiB）**，含 13,414 条简拼词条、148,443 条词对。模型只读 mmap，每次解码每个中间位置最多留 8 条路径。英文表沿用已有 523,993 字节，以 mmap 加约 160 KB 行偏移索引代替常驻字符串数组。模型文件映射体积和实际驻留峰值需分别在 Instruments 读取。[模型清单](../ios/Shared/dict/dict_meta.json) · [模型读取器](../ios/Shared/IMECore/ChatInitialsModel.swift) · [英文词表读取器](../ios/Shared/IMECore/EnglishLexicon.swift)
